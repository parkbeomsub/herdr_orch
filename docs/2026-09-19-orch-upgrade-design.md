# orch 고도화 설계 — 대화형 진입 · 스킬 자동 주입 · 팀 증설

- 작성일: 2026-09-19
- 대상: `/opt/homebrew/bin/orch` (968줄 bash), `~/.config/herdr/orch/`
- 상태: 설계 승인 완료, 구현 계획 대기

## 배경

orch는 herdr 워크스페이스에 오케스트레이터 1 + 에이전트 N 팬을 띄우는 도구다.
현재 플래그 기반 인터페이스는 충분히 성숙해 있으나 세 가지가 빠져 있다.

1. 진입 장벽 — 모든 옵션을 외워서 쳐야 한다. `--model`, `--wiki`는 이미 있지만 아무도 안 쓴다.
2. 에이전트가 운영 중 능력을 얻을 방법이 없다 — MCP·플러그인은 팀 생성 시점에 고정된다.
3. 한 워크스페이스에 팀이 하나뿐이다 — 기획팀을 돌리다 개발팀이 필요해지면 방법이 없다.

## 결정 사항

| 항목 | 결정 | 이유 |
|---|---|---|
| 마법사 발동 | 인자 없이 `orch` 만 칠 때 | 기존 스크립트·습관 불변. 플래그를 주면 즉시 실행 |
| 스킬 설치 범위 | 에이전트 cwd의 `.claude/skills/` | 60개 세션이 동시에 도는 환경에서 전역 오염 차단 |
| 스킬 설치 승인 | 사용자에게 묻지 않음 | 격리돼 있으므로 되돌리기가 디렉토리 삭제로 끝남 |
| 후보 선택 주체 | 오케스트레이터 | 사용자를 안 막을 뿐, 무엇을 깔지는 판단을 거친다 |
| 증설 팀 구조 | 새 탭 + 자체 오케스트레이터 | 오케 1인이 20명 넘게 관리하면 맥락이 터짐 |
| 팀 간 통신 | 오케↔오케 만 | 에이전트가 남의 팀 팬에 직접 쏘면 추적 불가 |

## 1. state 스키마 변경 (선행 작업)

### 문제

현재 `state/<ws>.json`은 워크스페이스당 팀 1개를 가정한다.

```json
{ "workspace": "w1J", "team": "", "orch_pane": "w1J:p2", "roles": [...] }
```

`orch_pane`과 `roles`가 최상위에 평평하게 있어, 같은 워크스페이스에 두 번째 팀을
만들면 첫 팀의 기록을 덮어쓴다. 그 결과:

- `--reharness` 가 두 번째 팀의 스펙으로 첫 팀 팬을 재기동한다
- `--stop` 은 애초에 state를 읽지 않고 **label 있는 팬을 전부** 닫는다 (orch:455-470).
  즉 기획팀을 정리하려 하면 개발팀까지 닫힌다

증설 기능의 실제 작업량은 탭 생성이 아니라 여기다.

### 신형 스키마

```json
{
  "version": 2,
  "workspace": "w1J",
  "teams": [
    { "tab": "w1J:t2", "tab_label": "orch",    "team": "dev",
      "cwd": "...", "spec": "...", "orch_pane": "w1J:p2",
      "model": "opus", "lead_model": "claude-opus-5[1m]",
      "created": "...", "roles": [ { "idx":0, "name":"PM", "slug":"pm", "pane":"w1J:p3" } ] }
  ]
}
```

### 마이그레이션

구버전 파일 5개(`w1, w15, w19, w1A, w1J`)가 존재한다. 읽는 시점에 승격한다.

- `version` 필드가 없으면 구형으로 판단
- 최상위 필드를 `teams[0]` 으로 감싸고 `tab` 은 `orch_pane` 의 탭으로 역산
- 승격 결과를 파일에 다시 쓴다 (한 번만 일어남)
- 승격 실패 시 원본을 `.bak` 으로 남기고 새로 시작

### 팀 선택 규칙

`--reharness` / `--stop` / `orch skill` 은 대상 팀을 정해야 한다.

1. `--tab <label>` 이 주어지면 그 탭의 팀
2. 없으면 **현재 포커스된 탭**의 팀
3. 포커스 탭에 팀이 없으면 `teams` 가 1개일 때만 그것, 여러 개면 목록을 보여주고 중단
4. `--all-teams` 로 전체 지정 (`--stop --all-teams` 가 기존 `--stop` 동작)

`--stop` 은 label 팬 전수 삭제를 버리고, 선택된 팀의 `orch_pane` + `roles[].pane` 만 닫는다.
state에 없는 확장 팬은 탭 소속으로 판별해 함께 닫는다.

**동작 변경 주의**: 지금까지 `--stop` 은 워크스페이스의 label 팬을 전부 닫았다. 앞으로는
포커스 탭의 팀만 닫는다. 팀이 하나뿐인 워크스페이스에서는 결과가 같지만, 종전 감각으로
치면 덜 닫힌 것처럼 보인다. 첫 실행 시 무엇을 닫을지 목록을 보여주는 기존 확인 절차를
유지하고, 대상이 워크스페이스 전체가 아님을 문구에 명시한다.

## 2. `--reharness --only <역할[,역할]>`

기존 reharness는 팀 전체를 재기동한다. 스킬을 한 역할에만 넣고 전체를 흔들 이유가 없다.

- `RH_PLAN` 배열을 구성한 뒤 `--only` 목록으로 필터링한다 (orch:780~845)
- 역할명은 팀 스펙의 `name` 또는 팬 label 로 매칭, 없으면 목록을 보여주고 중단
- 기존 동작(필터 없음)은 그대로

세션 resume·워크스페이스 경계 검증은 이미 구현돼 있으므로 건드리지 않는다.

## 3. `orch skill` — 에이전트 업그레이드

### 인터페이스

```
orch skill find <키워드>                    후보만 보여준다 (설치 안 함)
orch skill add <대상> --role <역할>          설치 + 그 역할만 재기동
orch skill list [--role <역할>]              지금 뭐가 깔려 있나
orch skill remove <이름> --role <역할>       제거 + 재기동
```

`<대상>` 해석: `owner/repo` 또는 `owner/repo#skill` 형태면 검색을 건너뛰고 바로 설치한다.
그 외는 키워드로 보고 검색부터 한다. 이 구분이 없으면 오케가 정확한 repo를 알고 있어도
불필요한 검색을 타게 된다.

`--role` 없으면 팀 전체 공용으로 설치한다 (cwd가 같으므로 물리적으로는 동일 위치,
차이는 팀 JSON 기록 여부).

### 동작

1. `npx skills find <키워드>` 로 후보 검색. 비대화형이어야 하므로 `--json` 유무를 먼저 확인하고,
   없으면 출력 파싱으로 폴백한다. 후보가 0개면 그 사실을 말하고 끝낸다
2. 후보가 여럿이면 첫 번째를 쓰지 않는다 — 오케스트레이터에게 목록을 돌려주고 고르게 한다
   (자동 선택은 엉뚱한 스킬을 조용히 설치하는 가장 흔한 실패다)
3. `cd <에이전트 cwd> && npx skills add <repo>` 로 설치. 전역 `-g` 는 절대 쓰지 않는다
4. 팀 JSON의 해당 역할 `skills` 배열에 기록 (`mcp`/`plugins` 와 동일 패턴)
5. `orch --reharness --only <역할>` 로 그 팬만 재기동 — `--resume` 이므로 대화 맥락 유지

### 팀 스펙 확장

```json
{ "name": "연구원", "mcp": [...], "plugins": [...], "skills": ["vercel-labs/skills#pdf-extract"] }
```

`validate_spec()` 에 `skills` 를 선택 필드로 추가한다. 팀 생성 시 이 배열을 순회해 설치한다.

### 안전장치

- 설치 대상 경로가 에이전트 cwd 하위인지 확인. 벗어나면 중단
- `npx` 부재 시 안내 후 중단 (`--doctor` 점검 항목에 추가)
- 네트워크 실패는 재시도하지 않고 사유를 그대로 보고한다

## 4. `orch --add-team <용도|팀> [--name <탭label>] [--roles ...]`

### 동작

1. 현재 워크스페이스에 새 탭 생성 (`herdr tab create --label orch-<용도>`)
2. 기존 생성 경로를 그대로 재사용해 오케 팬 + 에이전트 팬 배치
3. state의 `teams[]` 에 새 항목 추가 (기존 팀 항목은 불변)
4. 양쪽 오케 프롬프트에 상대 팀 정보를 주입한다

### 팀 간 통신

각 오케 프롬프트에 형제 팀 표를 넣는다.

```
## 같은 워크스페이스의 다른 팀
| 팀 | 탭 | 오케 팬 | 용도 |
|---|---|---|---|
| 기획 | orch | w1J:p2 | 요구사항·명세 |

규칙: 다른 팀에는 그 팀의 오케 팬에만 보낸다. 남의 팀 에이전트에 직접 보내지 않는다.
```

기존 팀 오케에도 새 팀을 알려야 하므로, 증설 후 기존 오케 팬에 안내 메시지를 1회 전송한다
(재기동 아님 — 진행 중 작업을 끊지 않는다).

## 5. 대화형 마법사

`$# -eq 0` 일 때만 발동. 각 답을 기존 플래그로 번역한 뒤 **실행될 명령을 그대로 보여주고** 확인받는다.

| 질문 | 기본값 | 번역 결과 |
|---|---|---|
| 용도 (개발/분석/기획/테스트/기타) | — | `--team <프리셋>` |
| 참고 위키/문서 디렉토리 | 없음 | `--wiki <경로>` |
| 에이전트 수 | 4 | 위치 인자 |
| 에이전트 모델 | `opus` | `--model` |
| 오케 모델 | `claude-opus-5[1m]` | `--orch-model` |

- 기타 선택 시 `--roles` 를 직접 입력받는다
- 위키 경로는 존재 확인 후 진행. 없으면 다시 묻는다
- 마지막 확인에서 n 이면 아무것도 만들지 않고 종료
- 비대화형(tty 없음)에서는 마법사를 띄우지 않고 기존 기본값으로 진행한다 — 스크립트 호환

### 신규 팀 프리셋 3종

`analysis`, `planning`, `qa` 를 기존 7종과 같은 형식으로 만든다.
각 9역할 이하, `flow`·`guides`·역할별 `prompt`/`mcp`/`plugins` 를 채운다.

## 테스트

기존 방식을 따른다: 숨김 워크스페이스를 만들어 검증 후 close.

```
ORCH_CLAUDE_CMD="echo x" ORCH_PLANNER_CMD=claude orch N --workspace <id>
```

| 대상 | 방법 |
|---|---|
| state 마이그레이션 | 구형 JSON 5개 사본으로 승격 → 결과 비교. 멱등성 확인 |
| 팀 선택 규칙 | 2팀 상태에서 `--reharness`/`--stop` 이 포커스 탭만 건드리는지 |
| `--only` 필터 | dry-run 출력에 지정 역할만 나오는지 |
| `orch skill` | `npx` 를 스텁으로 대체해 설치 경로가 cwd 하위인지 |
| `--add-team` | 기존 팀 state·팬이 그대로인지 |
| 마법사 | 입력을 파이프로 주입해 생성되는 명령줄 문자열 비교 |

주의: bash 3.2 + `set -e` 환경이다. 블록 마지막 줄의 `[ -n "$X" ] && printf` 는
X가 비면 스크립트를 죽인다. `if` 문으로 쓴다.

## 하지 않는 것

- 전역 스킬 설치 (`-g`)
- 팀 간 에이전트 직접 통신
- 기존 플래그 인터페이스 변경 — 마법사는 추가일 뿐 대체가 아니다
- 워크스페이스를 넘나드는 증설 — 증설은 항상 현재 워크스페이스의 새 탭
